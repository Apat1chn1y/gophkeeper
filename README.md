# GophKeeper

GophKeeper — клиент-серверная система для безопасного хранения и
синхронизации конфиденциальных данных: учётных данных, текстовых
заметок, бинарных файлов и банковских карт.

Проект выполнен как выпускная работа по языку Go.

## Возможности

- **Аутентификация**: регистрация, вход, JWT-сессии.
- **Управление данными**: четыре типа элементов (credentials, text,
  binary, card) с произвольными метаданными.
- **Синхронизация** между устройствами: инкрементальный push/pull,
  разрешение конфликтов по last-write-wins.
- **Шифрование в покое**: AES-256-GCM на стороне сервера, ключ не
  покидает окружение процесса.
- **Хеширование паролей**: bcrypt.
- **Локальная БД**: SQLite (без cgo).
- **CLI**: скриптуемый интерфейс для всех операций, включая загрузку
  бинарных данных из файла.
- **TUI**: интерактивный терминальный интерфейс на bubbletea.
- **OpenAPI**: спецификация протокола в `api/openapi.yaml`.

## Архитектура

```
┌────────────────────────────────────────────────────────────┐
│                     Клиент (cmd/client)                    │
│  ┌────────┐  ┌─────────────┐  ┌───────────┐  ┌──────────┐  │
│  │  CLI   │──│  localstore │──│   sync    │──│   api    │  │
│  └────────┘  │  (SQLite)   │  │  engine   │  │  (HTTP)  │  │
│  ┌────────┐  └─────────────┘  └───────────┘  └──────────┘  │
│  │  TUI   │                                                │
│  └────────┘                                                │
└─────────────────────┬──────────────────────────────────────┘
                      │ HTTP/JSON
┌─────────────────────┴──────────────────────────────────────┐
│                     Сервер (cmd/server)                    │
│  ┌──────────┐  ┌─────────┐  ┌──────────┐  ┌─────────────┐  │
│  │   api    │──│ service │──│ storage  │──│   crypto    │  │
│  │ (HTTP)   │  │ (rules) │  │(SQLite)  │  │ (AES-GCM)   │  │
│  └──────────┘  └─────────┘  └──────────┘  └─────────────┘  │
└────────────────────────────────────────────────────────────┘
```

Ключевые архитектурные решения:

- **Слоистая структура.** Транспорт (`api`), бизнес-логика (`service`),
  хранилище (`storage`), крипта (`crypto`) — независимы друг от друга.
  `storage` объявлен интерфейсом, поэтому SQLite можно заменить любой
  другой БД без изменения остального кода.
- **Шифрование в покое.** Сервер принимает plaintext, шифрует
  AES-256-GCM и только после этого пишет в БД. Ключ хранится в
  `GOPHKEEPER_ENCRYPTION_KEY`, никогда не пишется в БД и не логируется.
- **Синхронизация по LWW.** Каждый item несёт `updated_at`.
  При push сервер применяет last-write-wins: если у него уже есть
  более свежая копия, он возвращает её клиенту, и клиент обновляется.
  При pull клиент делает то же самое с учётом своего `dirty`-флага.
- **Soft-delete.** Удаления не стирают запись, а устанавливают
  `deleted_at` и монотонно увеличивают `updated_at`. Так tombstone
  распространяется на другие устройства через обычный pull.
- **Монотонность `updated_at`.** `service.Delete` никогда не выставляет
  метку времени меньше уже сохранённой, что защищает от клиентов с
  ушедшими вперёд часами.

## Быстрый старт

### Сборка

```bash
make build
```

Создаст `bin/server` и `bin/client`.

Собрать клиент и сервер под все поддерживаемые платформы:

```bash
make build-all
```

Создаст бинарники в `dist/` для Linux, macOS и Windows (amd64/arm64).

### Запуск сервера

```bash
cp config.env.example config.env
# Отредактируйте секреты в config.env
set -a; . ./config.env; set +a
./bin/server
```

По умолчанию слушает `127.0.0.1:8080`.

### Работа с клиентом

```bash
# Регистрация нового пользователя (сразу логинит)
./bin/client register -server http://127.0.0.1:8080 \
    -username alice -email a@x.io -password hunter2

# Добавить заметку (интерактивно спросит Title/Metadata/Data)
./bin/client add text

# Добавить заметку без интерактивных промптов
./bin/client add text -title "ssh key" -metadata "work"

# Добавить бинарный файл (содержимое читается из файла)
./bin/client add binary -from-file ./secret.pdf -title "passport scan"

# Синхронизация с сервером
./bin/client sync

# Список и вывод элемента
./bin/client list
./bin/client get <id>

# Удаление (soft-delete)
./bin/client delete <id>

# Интерактивный TUI
./bin/client tui
```

## Сценарии из ТЗ

**Новый пользователь:**
1. `client register` — регистрация + авто-логин, токен сохранён в
   `~/.gophkeeper/config.json`.
2. `client add <type>` — элемент пишется в локальную SQLite с флагом
   `dirty=1`.
3. `client sync` — dirty-элементы уходят на сервер, сервер возвращает
   canonical-версии, локальная копия обновляется, флаг снимается.

**Существующий пользователь:**
1. `client login` — токен выдаётся и сохраняется.
2. `client sync` — pull изменений с сервера с момента последнего
   успешного pull (`meta.last_sync`).
3. `client list` / `client get <id>` — запрошенные данные отображаются.
4. `client tui` — те же операции в интерактивном режиме.

## Протокол синхронизации

```
Клиент                                     Сервер
  │                                          │
  │ 1. POST /sync/push                       │
  │    {items: [dirty...]}                   │
  │ ───────────────────────────────────────► │
  │                                          │ LWW по updated_at
  │ ◄─────────────────────────────────────── │
  │    {items: [canonical...]}               │
  │                                          │
  │ 2. POST /sync/pull                       │
  │    {since: last_sync}                    │
  │ ───────────────────────────────────────► │
  │                                          │ ItemsSince
  │ ◄─────────────────────────────────────── │
  │    {items: [delta...], now: T}           │
  │                                          │
  │ 3. Локальный merge:                      │
  │    - нет локальной копии → принять       │
  │    - локально чисто → сервер победил     │
  │    - локально dirty → LWW; ничья серверу │
  │                                          │
  │ 4. Записать last_sync = T                │
```

Полная спецификация — в `api/openapi.yaml` (можно открыть в
https://editor.swagger.io).

## Безопасность

- **Пароли**: bcrypt с дефолтным work factor.
- **Сессии**: JWT HS256, секрет ≥32 байт, TTL настраивается.
- **Данные в покое**: AES-256-GCM, ключ в `GOPHKEEPER_ENCRYPTION_KEY`.
  Nonce генерируется `crypto/rand` для каждой записи.
- **Транспорт**: в dev-режиме HTTP; в продакшене — обязателен
  reverse-proxy с TLS. Это осознанное упрощение курсовой.

Что осознанно вне рамок проекта: клиентское E2E-шифрование с ключом,
производным от мастер-пароля (полноценная zero-knowledge модель),
2FA/TOTP, аппаратные токены.
