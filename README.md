# GophKeeper

GophKeeper — клиент-серверная система для безопасного хранения и
синхронизации конфиденциальных данных: учётных данных, текстовых
заметок, бинарных файлов и банковских карт.

Проект выполнен как выпускная работа по языку Go.

## Возможности

- **Аутентификация**: регистрация, вход, JWT-сессии. Пароли вводятся
  только интерактивно, без эха — флага `-password` нет.
- **Управление данными**: четыре типа элементов (credentials, text,
  binary, card) с произвольными метаданными.
- **Поиск**: серверный поиск по метаданным через `client list -search`.
- **Бинарные данные**: загрузка из файла через `-from-file` с
  понятной ошибкой при превышении лимита.
- **Синхронизация** между устройствами: инкрементальный push/pull,
  разрешение конфликтов по last-write-wins.
- **Шифрование в покое**: AES-256-GCM на стороне сервера, ключ не
  покидает окружение процесса.
- **Шифрование транспорта**: HTTPS всегда включён; self-signed
  сертификат генерируется при старте, если явная пара не задана.
- **Хеширование паролей**: bcrypt.
- **Локальная БД**: SQLite (без cgo).
- **CLI**: скриптуемый интерфейс для всех операций.
- **TUI**: интерактивный терминальный интерфейс на bubbletea.
- **OpenAPI**: спецификация протокола в `api/openapi.yaml`.

## Архитектура

```
┌────────────────────────────────────────────────────────────┐
│                     Клиент (cmd/client)                    │
│  ┌────────┐  ┌─────────────┐  ┌───────────┐  ┌──────────┐  │
│  │  CLI   │──│  localstore │──│   sync    │──│   api    │  │
│  └────────┘  │  (SQLite)   │  │  engine   │  │ (HTTPS)  │  │
│  ┌────────┐  └─────────────┘  └───────────┘  └──────────┘  │
│  │  TUI   │                                                │
│  └────────┘                                                │
└─────────────────────┬──────────────────────────────────────┘
                      │ HTTPS/JSON
┌─────────────────────┴──────────────────────────────────────┐
│                     Сервер (cmd/server)                    │
│  ┌──────────┐  ┌─────────┐  ┌──────────┐  ┌─────────────┐  │
│  │   api    │──│ service │──│ storage  │──│   crypto    │  │
│  │ (HTTPS)  │  │ (rules) │  │(SQLite)  │  │ (AES-GCM)   │  │
│  └──────────┘  └─────────┘  └──────────┘  └─────────────┘  │
└────────────────────────────────────────────────────────────┘
```

Ключевые архитектурные решения:

- **Слоистая структура.** Транспорт (`api`), бизнес-логика (`service`),
  хранилище (`storage`), крипта (`crypto`) — независимы друг от друга.
  `storage` объявлен интерфейсом, поэтому SQLite можно заменить любой
  другой БД без изменения остального кода.
- **Шифрование в покое.** Сервер принимает plaintext, шифрует
  AES-256-GCM и только после этого пишет в БД. Ключ хранится в
  `GOPHKEEPER_ENCRYPTION_KEY`, никогда не пишется в БД и не логируется.
- **TLS всегда включён.** `http.Server` работает только через HTTPS.
  Явная PEM-пара задаётся через `GOPHKEEPER_TLS_CERT`/`_KEY`; иначе
  сервер генерирует self-signed сертификат для `localhost` в памяти.
  Отдельного plaintext-режима нет.
- **Синхронизация по LWW.** Каждый item несёт `updated_at`.
  При push сервер применяет last-write-wins: если у него уже есть
  более свежая копия, он возвращает её клиенту, и клиент обновляется.
  При pull клиент делает то же самое с учётом своего `dirty`-флага.
- **Soft-delete.** Удаления не стирают запись, а устанавливают
  `deleted_at` и монотонно увеличивают `updated_at`. Так tombstone
  распространяется на другие устройства через обычный pull.
- **Монотонность `updated_at`.** `service.Delete` никогда не выставляет
  метку времени меньше уже сохранённой, что защищает от клиентов с
  ушедшими вперёд часами.
- **Сериализация доступа к SQLite.** Пул соединений ограничен одним
  (`SetMaxOpenConns(1)`) и для сервера, и для клиента: это исключает
  гонки при DEFERRED-транзакциях и `SQLITE_BUSY`. Параллелизм
  HTTP-слоя при этом полностью сохраняется — БД всё равно одна.
- **Уникальность username — на уровне схемы.** `CreateUser` делает
  `INSERT` напрямую, а не проверяет через предварительный `SELECT`.
  Нарушение `UNIQUE` транслируется в `storage.ErrDuplicate`, что даёт
  корректный HTTP 409 вместо 500 при конкурентной регистрации.

## Быстрый старт

### Сборка

```bash
make build
```

Создаст `bin/server` и `bin/client`.

Собрать клиент и сервер под все поддерживаемые платформы:

```bash
make build-all
```

Создаст бинарники в `dist/` для Linux, macOS и Windows (amd64/arm64).

### Запуск сервера

```bash
cp config.env.example config.env
# Отредактируйте секреты в config.env
set -a; . ./config.env; set +a
./bin/server
```

По умолчанию сервер слушает `https://127.0.0.1:8080` и использует
сгенерированный в памяти self-signed сертификат. Чтобы использовать
свой PEM-сертификат, задайте `GOPHKEEPER_TLS_CERT` и `GOPHKEEPER_TLS_KEY`.

### Работа с клиентом

```bash
# Регистрация. Пароль будет запрошен интерактивно, без эха.
./bin/client register -server https://127.0.0.1:8080 \
    -username alice -email a@x.io

# Вход. Пароль тоже вводится интерактивно.
./bin/client login -server https://127.0.0.1:8080 -username alice

# Добавить заметку (интерактивно спросит Title/Metadata/Data)
./bin/client add text

# Добавить заметку без интерактивных промптов
./bin/client add text -title "ssh key" -metadata "work"

# Добавить бинарный файл. Размер ограничен 700 KiB (см. раздел
# «Ограничения»), чтобы base64+JSON укладывались в лимит сервера.
./bin/client add binary -from-file ./secret.pdf -title "passport"

# Синхронизация с сервером
./bin/client sync

# Список, поиск и вывод элемента
./bin/client list
./bin/client list -search github
./bin/client get <id>

# Удаление (soft-delete)
./bin/client delete <id>

# Интерактивный TUI
./bin/client tui
```

### Пароли и `-password`

Флаг `-password` **не поддерживается** ни в `register`, ни в `login`.
Пароль всегда запрашивается интерактивно:

- если stdin — терминал, ввод читается через `term.ReadPassword` и
  не отражается на экране;
- если stdin — pipe или файл (например, при тестах), пароль читается
  как обычная строка.

Это сделано осознанно: флаг виден в списке процессов (`ps aux`) и
сохраняется в истории оболочки.

## Сценарии из ТЗ

**Новый пользователь:**
1. `client register` — регистрация + авто-логин, токен сохранён в
   `~/.gophkeeper/config.json`.
2. `client add <type>` — элемент пишется в локальную SQLite с флагом
   `dirty=1`.
3. `client sync` — dirty-элементы уходят на сервер, сервер возвращает
   canonical-версии, локальная копия обновляется, флаг снимается.

**Существующий пользователь:**
1. `client login` — токен выдаётся и сохраняется.
2. `client sync` — pull изменений с сервера с момента последнего
   успешного pull (`meta.last_sync`).
3. `client list` / `client list -search <q>` / `client get <id>` —
   запрошенные данные отображаются.
4. `client tui` — те же операции в интерактивном режиме.

## Протокол синхронизации

```
Клиент                                     Сервер
  │                                          │
  │ 1. POST /sync/push                       │
  │    {items: [dirty...]}                   │
  │ ───────────────────────────────────────► │
  │                                          │ LWW по updated_at
  │ ◄─────────────────────────────────────── │
  │    {items: [canonical...]}               │
  │                                          │
  │ 2. POST /sync/pull                       │
  │    {since: last_sync}                    │
  │ ───────────────────────────────────────► │
  │                                          │ ItemsSince
  │ ◄─────────────────────────────────────── │
  │    {items: [delta...], now: T}           │
  │                                          │
  │ 3. Локальный merge:                      │
  │    - нет локальной копии → принять       │
  │    - локально чисто → сервер победил     │
  │    - локально dirty → LWW; ничья серверу │
  │                                          │
  │ 4. Записать last_sync = T                │
```

Полная спецификация — в `api/openapi.yaml` (можно открыть в
https://editor.swagger.io).

## Поиск по метаданным

`GET /api/v1/items?q=<substring>` возвращает не удалённые items
пользователя, у которых `metadata` содержит подстроку (регистронезависимо
для ASCII). Спецсимволы `%`, `_` и `\` в запросе экранируются и
матчатся буквально.

CLI-обёртка: `client list -search <substring>`. Если запрос пустой —
сервер возвращает весь список (поведение `client list`).

## Ограничения

**Размер загружаемых файлов.** Сервер ограничивает тело запроса
1 МиБ (`api.maxBodyBytes`). Кодирование base64 и JSON-обёртка
добавляют около 33% к размеру, поэтому `client add binary -from-file`
отказывает при файлах больше **700 KiB** — с сообщением, объясняющим
причину, до чтения файла в память. Для больших файлов потребовалась бы
загрузка чанками, что выходит за рамки курсовой.

**Локальное хранилище в открытом виде.** Клиентская SQLite хранит
items в plaintext; шифрование в покое выполняется на сервере. В
продакшене клиент должен шифровать локальную БД ключом, производным
от мастер-пароля пользователя — этот слой вне рамок проекта.

**TLS-верификация.** Клиент по умолчанию не проверяет сертификат
сервера (`InsecureSkipVerify`) — предполагается dev-развёртывание с
self-signed сертификатом. Для продакшена нужен либо клиент с
собственным CA pool, либо pinning по SHA-256 отпечатку, который сервер
логирует при старте.

## Безопасность

- **Пароли**: bcrypt с дефолтным work factor. Никогда не принимаются
  флагом командной строки — только интерактивный ввод без эха.
- **Сессии**: JWT HS256, секрет ≥32 байт, TTL настраивается.
- **Данные в покое**: AES-256-GCM, ключ в `GOPHKEEPER_ENCRYPTION_KEY`.
  Nonce генерируется `crypto/rand` для каждой записи.
- **Транспорт**: HTTPS всегда включён (TLS 1.2+). Self-signed
  сертификат по умолчанию или явная PEM-пара через
  `GOPHKEEPER_TLS_CERT`/`_KEY`.
- **Уникальность пользователей**: гарантируется схемой БД
  (`UNIQUE username`), а не проверкой приложения.

Что осознанно вне рамок проекта: клиентское E2E-шифрование с ключом,
производным от мастер-пароля (полноценная zero-knowledge модель),
2FA/TOTP, аппаратные токены, загрузка больших файлов чанками,
cert pinning на клиенте.
